# Trust and Safety Benchmark: 4 e-commerce компании

Сравнительное исследование паттернов фрода, фиктивных отзывов и аномальных отмен на четырёх реальных онлайн-ритейл площадках. Полный текст с методологией, оговорками и ограничениями - в report/cross_company_synthesis.md.

## Компании и датасеты

| Компания | Датасет | Что закрывает |
|---|---|---|
| Olist, Бразилия | kaggle.com/datasets/olistbr/brazilian-ecommerce | Граф продавец-покупатель, аномальные продавцы, накрутка отзывов |
| Fraud E-Commerce, США | kaggle.com/datasets/vbinh002/fraud-ecommerce | IP и device паттерны мошеннических платежей, финансовый эффект от задержки блокировки |
| UCI Online Retail, Великобритания | archive.ics.uci.edu/dataset/352 | Аномалии отмен заказов |
| Instacart, США | kaggle.com/datasets/psparks/instacart-market-basket-analysis | Поведенческий baseline |

## Структура проекта

- src/schema_mapping.py - загрузка всех источников в единую схему событий
- src/shared_features.py - общий feature engineering для anomaly detection
- notebooks/01_olist_anomaly_detection.py - Isolation Forest и rule-based флаги на продавцах Olist, работает напрямую с SQLite базой
- notebooks/02_review_check.py - проверка отзывов у flagged продавцов на Olist
- notebooks/03_fraud_ecommerce_ip_patterns.py - IP и device анализ на Fraud E-Commerce
- notebooks/05_geo_fraud_analysis.py - гео-разрез fraud rate по странам
- notebooks/06_uci_instacart_analysis.py - anomaly detection на UCI Retail и Instacart
- notebooks/07_financial_impact.py - расчёт предотвратимой выручки в зависимости от скорости блокировки
- report/ - все результаты в виде csv, плюс финальный синтез cross_company_synthesis.md

## Как запустить

Olist читается напрямую из SQLite базы. Если у вас уже есть olist_db.db, положите файл в корень проекта, рядом с README.md. Если базы нет, её можно собрать через любой скрипт импорта CSV в SQLite, либо адаптировать load_olist в schema_mapping.py под чтение из CSV напрямую.

Для остальных источников скачайте датасеты по ссылкам выше и положите файлы в соответствующие папки data/имя_компании, точный список ожидаемых файлов и их названия - в docstring и коде schema_mapping.py.

Установите зависимости:

pip install pandas scikit-learn numpy

Запустите нужный модуль, например:

python notebooks/01_olist_anomaly_detection.py

## О качестве исходных данных

На датасете Fraud E-Commerce один из сигналов оказался подозрительно чистым: все транзакции, совершённые меньше чем через минуту после регистрации аккаунта, оказались мошенническими без единого исключения, доля сто процентов. В реальных данных такая идеальная закономерность практически никогда не встречается, обычно есть хотя бы небольшой процент шума. Это признак того, что либо датасет частично синтетический, либо при его сборке заложили слишком прямолинейное правило генерации фрода.

Я сознательно не стала скрывать этот момент. Такой результат нельзя переносить на реальный продакшн без проверки на менее чистых данных, и его стоит воспринимать скорее как сигнал о специфике конкретного датасета, а не как универсальный закон поведения мошенников.

Похожая ситуация была и с гео-разрезом по странам: разница в доле мошеннических транзакций между странами показалась заметной, но при более внимательном рассмотрении оказалось, что самые высокие цифры получены на выборках в сто с небольшим транзакций, где один-два случая сильно смещают процент.

## Ключевые результаты

### Фрод и фиктивные отзывы

На Fraud E-Commerce, где есть настоящие метки мошенничества, подтвердились три сильных сигнала:

- устройство, с которого заходили два и более разных аккаунта - fraud rate 31 % против 3 % у обычных устройств
- IP-адрес, с которого заходили два и более аккаунта - 90 % против 4,6 %
- покупка в первую минуту после регистрации - 100 % фрода среди таких транзакций

На Olist, где меток фрода нет, тот же принцип узкого круга связей нашёл продавцов с почти всеми заказами от одного-двух покупателей и почти стопроцентной отменой заказов, а у части из них - подозрительно позитивные отзывы на фоне этих отмен.

### Аномальные отмены

Фичи на основе концентрации покупателей работают только на настоящих маркетплейсах с двумя разными сторонами сделки, продавцом и покупателем. На одностороннем ритейлере, UCI Retail и Instacart, эти фичи не дают полезного сигнала - для таких компаний нужна другая методология, основанная на отклонении от собственной истории клиента.

### Финансовый эффект от задержки блокировки

На Fraud E-Commerce мошеннические транзакции принесли 523 488 условных единиц выручки. Если бы блокировка срабатывала автоматически при появлении двух разных аккаунтов на одном устройстве, можно было бы предотвратить 57,7% этой суммы. При пороге в десять аккаунтов - только 10%. Разница между этими двумя сценариями - 249 514 в предотвращённой выручке, это и есть цена задержки решения.
